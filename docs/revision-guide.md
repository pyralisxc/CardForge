# CardForge: understanding this revision

This guide is a starting point for reading the product and source **at the Git revision containing it**. It is not a deployment report or a complete independent verification of every workflow. The [greater product blueprint](https://pyralisholdings.atlassian.net/wiki/spaces/PYPH/pages/590018) records future direction and decisions across branches; its [version roadmap](https://pyralisholdings.atlassian.net/wiki/spaces/PYPH/pages/1966082) sets milestone goals, not proof of what this revision contains. The [agent map](agent-map.md) routes implementation work, while [architecture](architecture.md), [integration ownership](integrations.md), [operations](operations.md), [testing](testing.md), and the [risk register](risk-register.md) retain their existing responsibilities.

## How to read and verify

- **Source observation** describes what the inspected code expresses at a particular revision. Source is evidence of implementation, not proof that it ran or that a user could complete the experience.
- **Documented expectation** describes a contract in repository prose. Validate the relevant behavior against source and, when consequential, execute the appropriate tests or real journey. [Product direction](product-direction.md) contains a mix of context and intended experience; its statements are not automatically source-observed.
- **Executed evidence** must identify the revision, command or journey, and important boundaries such as mocked providers. A test file or CI definition by itself does not prove it ran.
- **Deployment evidence** must identify the environment and deployed revision; live provider configuration, authorization, and external effects require separate verification. A branch, source description, or passing local test does not prove them.
- **Unknown** means not established, not absent. Source links below are entry points; follow callers, tests, actual access conditions, and failure paths before relying on a consequence.

They are not claims of hosted execution, and inspection does not cover every branch of each linked owner. This document ships in a later commit: use Git history to identify changes since an observation and recheck the source at the revision under review.

## Planning differences that affect the foundation milestone

The ownership and package-scope observations below were rechecked against Preview source `a36f83965f46f75070b7a7644a7ae2fed47ba465`. They are source findings, not browser/provider acceptance or claims about unmerged fixes.

- **Independent Sets are the goal, not the current Template model.** [Set duplication](../src/features/project/store/settingsSlice.ts) gives the Set and cards new identities but retains referenced Template IDs. [Template changes and deletion](../src/features/project/store/templateSlice.ts) operate on shared collections and referring cards. The [Studio and Sets blueprint](https://pyralisholdings.atlassian.net/wiki/spaces/PYPH/pages/622613) instead wants Set-owned Templates. Reconcile identity, migration, and destructive behavior before implementing that transition.
- **A Set filename does not prove a Set-only download.** The [project-file export action](../src/features/project/hooks/useProjectFileActions.ts) captures the current project document, then names it from an active/first Set. The [workspace-document owner](../src/features/project/client/projectWorkspaceDocument.ts) also exposes a distinct Set-isolating capture. Check the exact caller and reopen/collision behavior rather than treating these paths as equivalent.
- **Resource revisions do not settle the new creator-history design.** Existing exact Pipeline revisions and provider save-conflict controls are not a decision on the desired Set Updates, named paths, comparison engine, or portable review ledger. [Studio and Sets](https://pyralisholdings.atlassian.net/wiki/spaces/PYPH/pages/622613) retains that unresolved design; [Delivery and Verification](https://pyralisholdings.atlassian.net/wiki/spaces/PYPH/pages/983041) routes the pre-implementation decisions.
- **Saving defaults differ from the clarified interaction.** At the same inspected source, the enabled [Drive working session](../src/features/project/client/googleDriveWorkingSession.ts) schedules dirty saves after `4_000` ms. The inspected [experience-settings schema](../src/features/experience-settings/model/experienceSettings.ts) contains presentation, consent and starter-Template settings, not the desired autosave frequency/trigger controls. [Product Direction](product-direction.md#save-semantics) now requires manual Save initially, optional configurable autosave, and automatic revision/persistence mechanics after either permitted trigger. This is an implementation gap, not a claim that the default has changed in Preview.
- **Defaults, capabilities and authority are not interchangeable.** The current [experience-settings route](../src/app/api/owner/experience-settings/route.ts) uses the shared Owner check; independent website/product ownership remains blueprint direction. [Project capabilities](../src/domain/entitlements/index.ts) allow portable project files for every access mode while distinguishing clean finished output; [account entitlement](../src/features/account/lib/accountEntitlement.ts) keeps commercial plan and authority separate. Neither an Owner preference nor a paid plan invents provider permission, capacity or live availability. These are source observations, not authenticated runtime acceptance.

## Journey: enter work and navigate its context

1. The account route composes the creator environment and accepts context such as section, focus, tool, and return context. Inspect the [account route](../src/app/account/page.tsx) and [Desk controller](../src/features/desk/hooks/useDeskController.ts), not just a URL, to determine access and initialization for a particular entry.
2. Desk discovery has its own [work discovery owner](../src/features/desk/hooks/useDeskWorkDiscovery.ts). Browser work and provider, campaign, or temporary-document projections have different authorities and availability. A source failure must not be interpreted as proof there is no work; check the specific scope and UI state.
3. The Desk controller uses a selected Set, focus and contextual-tool navigation. The focused Artifact surface has an edit mode with **Save & Done** or **Done**, **Cancel**, an all-fields action, and separate browse/zoom controls: see [focused Artifact workspace](../src/features/desk/components/FocusedArtifactWorkspace.tsx). Those source controls alone do not prove a usable end-to-end keyboard, screen-reader, touch, or small-screen experience.
4. `/studio` without a document or output reference redirects to the account Design entry; other handoffs must be traced through the [Studio route](../src/app/studio/page.tsx) and their exact target. Do not assume every path into Studio is the same workflow.

For documented interaction expectations, see [spatial model](product-direction.md#spatial-model) and [architecture: core ownership](architecture.md#core-ownership). For source owners and likely tests see [Studio surfaces and navigation](agent-map.md#studio-surfaces-and-navigation). **Not established by this pass:** end-to-end creation, navigation restoration, accessibility, every selection/action combination, and hosted account or provider behavior.

## Journey: create and edit a card Set

1. Desk's create action creates and activates an `Untitled Set`, starts rename, and focuses that Set or opens Design according to its entry action. Desk resolves the local Set before opening context tools; provider work has a separate preparation path. Inspect the [Desk controller](../src/features/desk/hooks/useDeskController.ts) and [Set state](../src/features/project/store/settingsSlice.ts). Creation alone does not prove that a durable copy was written.
2. Choose an Artifact in the Set and enter Edit to change its content; the focused workspace exposes **Save & Done** when dirty, **Done** otherwise, **Cancel**, and **All fields**. Design changes the referenced Template rather than treating Template structure as an Artifact content field. The [focused Artifact workspace](../src/features/desk/components/FocusedArtifactWorkspace.tsx) is the entry to trace actions and [Artifact commands](../src/features/desk/hooks/useArtifactCommands.ts) owns selected operations. Direct-edit compatibility and incomplete or missing Template behavior must be checked for the exact selection.
3. In Template Design, the [editor top bar](../src/features/template-editor/components/TemplateEditorTopBar.tsx) and [save commands](../src/features/template-editor/hooks/useTemplateEditorCommands.ts) expose the draft, undo/redo and save boundary. The save code distinguishes an unsuccessful save, a successful local commit whose canonical readback is unavailable, and an earlier saved snapshot while newer edits remain. A status about one of these outcomes must not be described as a successful provider copy or Pipeline publication.
4. The [bulk generator](../src/features/card-generator/components/BulkGenerator.tsx) offers generation and revision, input/mapping and a revision preview. An ambiguous revision prevents the proposed commit; the interface exposes undo for a prior bulk revision. Inspect the actual parser and revision plan before promising semantics for omitted columns or explicit blank values.
5. The [project import/export owner](../src/features/project/hooks/useProjectFileActions.ts) presents a decoded import preview and merge/replace choice before application. Project download, separate Set-specific location saves, and finished rendered output are different operations; check their scope before telling someone what is included.

Test definitions for navigation, editor handoff, import durability and output include [Desk tool context](../tests/product/workflows/desk-tool-context.spec.ts), [Template canvas handoff](../tests/product/workflows/template-canvas-handoff.spec.ts), [project import durability](../tests/product/unit/project-import-durability.test.ts), and [output artifacts](../tests/product/workflows/output-artifacts.spec.ts). A test definition is not a record that it ran. **Not established:** complete selection/gesture matrix, every save/import caller, real package/output bytes, accessibility, and hosted behavior.

## Journey: duplicate, save, export, and reopen work

These are distinct commitments; do not treat a success in one as proof of another.

- **Duplicate a local Set:** the [Set duplication implementation](../src/features/project/store/settingsSlice.ts) creates a new Set ID and new IDs for its cards and organization tags, remaps card positions, and copies the source Set's Template references. The [Desk command](../src/features/desk/hooks/useDeskController.ts) invokes it for a local Set. The copy's card identities differ, but retaining the Template references does **not** establish independently Set-owned Templates. The blueprint's independent Set ownership is a future direction requiring reconciliation and migration.
- **Browser working copy:** inspect the [project persistence owner](../src/features/project/persistence) and [storage lanes](architecture.md#browser-workspace) for account scope, persistence, conflict and recovery. A browser working-copy status is not by itself proof of a current device or provider copy.
- **Download/project export:** [project file actions](../src/features/project/hooks/useProjectFileActions.ts) capture the current project document and derive the package name from the active Set where available; the snapshot is constructed through [browser package capture](../src/features/project/client/browserProjectPackage.ts). A Set-derived filename is not evidence that this particular export captured only one Set. Other Set-specific save and package paths must be evaluated on their own callers rather than assumed to have the same scope.
- **Location-specific saves and reopening:** [work-location capabilities](../src/features/project/model/workLocations.ts), [local-folder adapter](../src/features/project/client/localProjectFolder.ts), and [Drive transfer owner](../src/features/project/client/googleDriveProjectTransfer.ts) are different paths. See [user-owned durable locations](architecture.md#user-owned-durable-locations). Permission, conflict, readback, copy and move behavior must be verified at the exact path; do not generalize one provider's guarantees to another.
- **Import/reopen:** trace the chosen entry through [project file actions](../src/features/project/hooks/useProjectFileActions.ts), package decode and application before assuming which workspace objects are affected. The desired one-Set portable behavior and older multi-Set compatibility are separate concerns.

### Browser, folder, Drive and temporary-document boundaries

The [account workspace bootstrap](../src/features/project/client/accountProjectWorkspace.ts) attempts guest adoption, hydrates the scoped workspace and performs the configured cleanup before the editor mounts. The [guest adoption owner](../src/features/project/persistence/guestWorkspaceAdoption.ts) distinguishes an absent account workspace from an existing one; do not assume signing in replaces existing account work with guest work. Its conflict message tells the creator to preserve or export work in a tab before loading a newer browser copy. The [atomic application owner](../src/features/project/client/projectWorkspaceDocument.ts) is the relevant import/commit path; inspect its checks before describing cancellation, concurrent edits or imported identity handling.

For an attached local folder, [revision checking](../src/features/project/client/localProjectFolder.ts) refuses a missing, unreadable or changed project rather than simply overwriting it. Drive's [transfer owner](../src/features/project/client/googleDriveProjectTransfer.ts), [working session](../src/features/project/client/googleDriveWorkingSession.ts) and [link repair](../src/features/project/client/googleDriveLinkRepair.ts) have their own account, provider and package revision boundaries. An unconfirmed result, a confirmed provider write whose local link failed, and a failed write are not interchangeable; read exact state/receipts before retrying.

For agent work against a connected project, the [MCP project bridge](../src/features/studio-documents/server/mcpProjectSourceBridge.ts) inspects exact provider/package revisions, creates a temporary Studio-document checkout and checks lineage on commit. The [browser handoff](../src/features/studio-documents/hooks/useStudioDocumentHandoff.ts) is a separate installation path. Browser-only work does not become remotely available merely because an agent exists. The source's revision preflight is not proof of provider-level atomic concurrency protection or of a deployed MCP connection.

Relevant test definitions include [account persistence](../tests/product/unit/studio-account-persistence.test.ts), [atomic application](../tests/product/unit/project-atomic-apply.test.ts), [project source conflicts](../tests/product/unit/project-source-conflicts.test.ts), [Drive link repair](../tests/product/unit/google-drive-link-repair.test.ts), and [MCP project bridge](../tests/product/unit/mcp-project-source-bridge.test.ts). They are pointers to assertions, not a claim of execution or live provider coverage.

**Not established by this pass:** real exported bytes with multiple Sets and prepared Templates, collision-safe round trips, cancelled or failed writes, every import entry, simultaneous clients, live Drive/local-folder behavior, and deployed UX. Relevant known-risk and verification context: [risk register](risk-register.md), [testing](testing.md), and [project/storage routing](agent-map.md#projects-storage-and-library).

## Journey: account, access, and billing

The [account route](../src/app/account/page.tsx) composes Desk, Library and Profile based on the requested context. If entitlement lookup fails, it records an unavailable state; do not interpret unavailable account/provider data as a confirmed paid or Free outcome. Profile's [management page](../src/features/account/components/ProfileManagementPage.tsx) also has sign-in configuration and loading states. The [contributor access projection](../src/features/contributor-access/model.ts) is tied to eligibility and session identity; an active Contributor's scopes and Owner authority are distinct from a commercial plan.

The [checkout route](../src/app/api/billing/checkout/route.ts) rejects unsigned users, validates the plan and requests a Stripe Checkout session. The separate [billing portal route](../src/app/api/billing/portal/route.ts) requires a signed-in account and linked customer and validates the return destination. Session creation is not payment completion or an entitlement update. The [webhook processor](../src/features/billing/server/processStripeWebhook.ts) and [subscription access synchronization](../src/features/billing/server/syncSubscriptionAccess.ts) are separate boundaries: synchronization locks the user, re-reads Stripe subscriptions and may fail when storage or a complete provider read is unavailable. Do not infer live account configuration, successful subscription changes, or Marketplace credits from these source paths.

Test definitions include [account entitlement](../tests/product/unit/account-entitlement.test.ts), [billing current entitlement](../tests/product/unit/billing-current-entitlement.test.ts), and [account workspace lifecycle](../tests/product/workflows/account-workspace-lifecycle.spec.ts); their presence does not prove execution here. **Not established:** end-to-end signed-in UI, payment or portal completion, webhook delivery, provider account settings, or deployed authorization. See [identity and billing](agent-map.md#identity-billing-and-access) and [integration ownership](integrations.md).

## Journey boundaries: Pipeline review and site operations

Library's [scope model](../src/features/storage-management/model/libraryScopes.ts) distinguishes Personal, Pipeline, Published and capability-gated Campaigns. Published represents the person's own published contributions and is exposed to Contributors or Owners; Pipeline represents shared work visible to the account. Loading, unavailable, partial, empty and ready are distinct states. [Library actions](../src/features/storage-management/hooks/useAccountLibraryActions.ts) route local Sets to Desk and local Templates to Design; a published Set installation creates browser work. A copied Set's independent local identity must not be confused with independent ownership of all referenced Templates in every duplication path.

An eligible Contributor may send a local Set to Pipeline; generic uploads have their own [validation and persistence owner](../src/features/pipeline/lib/pipelineUploadSubmission.ts). The [Pipeline vote route](../src/app/api/pipeline/%5BsubmissionId%5D/vote/route.ts) requires `assets.review`; the [submission route](../src/app/api/pipeline/%5BsubmissionId%5D/route.ts) has different scoped submission and Owner checks for particular operations. Item visibility is not permission to perform a different action, and submission, review and publication are distinct commitments. Inspect [visibility policy](../src/features/pipeline/lib/pipelineVisibility.ts) and the exact selected revision rather than substituting a similarly named or latest item.

Revision recovery and catalog-lineage Trash are separate boundaries: [revision recovery](../src/features/pipeline/server/revisionRecovery.ts) checks Owner or active scoped Contributor access and the exact expected state; [catalog Trash](../src/features/pipeline/server/catalogTrash.ts) checks Owner access and passes the expected identity/state to its native command. Conflict, dependency and unconfirmed outcomes require reading exact state rather than an automatic repeat. Source and migration definitions do not prove the current deployed database, cleanup schedule, or a particular user's permissions. Test definitions include [Library contextual review](../tests/product/workflows/library-context-review.spec.ts) and [revision recovery](../tests/product/workflows/revision-recovery.spec.ts); they are not execution evidence.

The [Owner route](../src/app/owner/page.tsx) checks server-resolved access. As one operation-specific example, the [website revision route](../src/app/api/owner/website-revisions/route.ts) checks Owner identity and receives an expected revision or generation for the corresponding save/activation command. The [marketing dispatcher](../src/features/marketing-distribution/server/dispatcher.ts) distinguishes known failed from uncertain publication and can leave uncertain outcomes `unknown` rather than scheduling a blind retry. These examples do not establish authority or recovery behavior for every Owner or marketing action.

For public feedback, the [roadmap page](../src/features/roadmap/components/RoadmapPage.tsx) composes account context with the [roadmap panel](../src/features/roadmap/components/RoadmapPanel.tsx); operations and status controls depend on the exact action and authority. The [contact route](../src/app/api/contact/request/route.ts) validates and rate-limits requests, attempts to record the request and send email, and reports an email failure when delivery cannot be confirmed. The record attempt can return no ID, so a successful email response does not prove an inbox record exists. A submitted form or stored request is not evidence that support read or resolved it, and source does not prove live email delivery.

**Not established:** complete Pipeline voting, revision, publication or Trash outcomes; end-to-end site-editing and support journeys; live roles and provider effects. Start with [Pipeline](agent-map.md#pipeline-and-publication), [public/Owner/legal/roadmap](agent-map.md#public-owner-legal-and-roadmap), and [marketing](agent-map.md#marketing-and-delivery).

## Keep this guide correct as the code changes

When a change alters an important user journey, access rule, persistence boundary, recovery path, or documented limitation, review the relevant narrative and evidence in the same change. Update or explicitly mark outdated observations, preserve source links, and identify what was actually verified. Reviewers may use Development Intelligence and the [affected-verification report](agent-map.md), but structural coverage or a passing check does not prove UX or documentation accuracy. Do not duplicate machine-generated graphs in prose or add an automatic prose rewrite as a substitute for review.

## How documentation travels to Main

These same files are versioned with the source. A normal Preview-to-Main merge carries the included documentation changes with the code; it does not automatically rewrite or re-verify their meaning. Prefer **this revision** over claims that a feature exists merely because the page is on a particular branch. Label environment-dependent procedures and actual runtime observations separately.

Before requesting production approval, compare the exact Preview candidate with the destination and inspect material documentation, especially source/UX claims, limitations, configuration-dependent behavior, broken links, and any future-versus-current differences. Do not silently describe a planned feature as shipped. Present the stable Preview review link, scope, and exact SHA and obtain explicit approval for that SHA as required by [operations](operations.md). A later documentation-only commit still changes the candidate SHA and requires approval of the new exact candidate. If conflict resolution or other merge changes alter the resulting tree, verify the resulting Main revision. A merge is not evidence of deployment, provider readiness, or successful runtime behavior. Update relevant Confluence status/evidence only when supported; it is not an automatic copy of branch documentation.
