# CardForge Architecture

Last updated: September 26, 2026

CardForge is a live local-first card production studio at `https://cardforges.com`. This document describes current product ownership and runtime invariants only. Historical rollout steps belong in Git/provider history; provider-specific ownership details belong in `docs/integrations.md`.

## Product truth

- Public product: `/`, `/about`, `/cameron`, `/roadmap`, `/contributors`, `/contact`, and legal pages.
- Creator environment: Desk at `/account` owns working context. `CreatorInteractionSession` owns creator focus, selection, camera, lens, and tool-stack state, while the shared Environment presentation contract derives Browse/Focus/Edit/Task depth from that state. Design, Generate, Output, Pipeline, and storage/location controls are lazy contextual tools layered over Desk or Library. `/studio` is compatibility ingress for an exact temporary Studio document and otherwise redirects to Desk Design.
- Desk discovery independently projects scoped browser work, authorized Google Drive projects, remembered local-folder work, and private Studio documents. It follows native provider cursors, retains same-account results only for transient source failures, clears protected projections on scope/access changes, and distinguishes loading, empty, unavailable, permission-required, and temporary states. Proven work IDs/provider bindings—not display names—pool related copies; folder-only remembered work remains a location object until the user explicitly reconnects it.
- Desk tool launches preserve focused Set/Artifact identity. Artifact-scoped Design and Generate resolve the Artifact's current front/back Template relationship; Set-level Generate uses an unambiguous referenced Template or requires an explicit Template choice when several are available. It never chooses an arbitrary first card as design authority. A launch waits for required Templates through the existing Library bootstrap, without replacing missing Templates or clearing a card back; changing focus cancels the pending launch. The context rail owns closing non-modal Desk tools, so their visually hidden headings contain no duplicate keyboard control.
- Account/access: Clerk identifies users; CardForge applies free, Creator Pass, Designer Pass, contributor, and owner policy.
- Billing: Stripe owns Checkout, subscriptions, customers, webhooks, and Billing Portal state; CardForge maps eligible product subscriptions into application access.
- Shared platform state: Supabase owns CardForge shared records, temporary private Studio documents, and approved managed media.
- User projects: Templates, generated cards, project uploads, preferences, and project files use the browser-local workspace as the normal working copy. Durable copies belong in portable `.cardforge`/Set files, user-authorized local folders, or connected providers such as Google Drive; arbitrary local workspace state is not automatically uploaded. Browser-save status therefore describes the working copy only, not the freshness of any provider/package snapshot.
- Email: Resend owns delivery; CardForge owns support/contributor request validation/routing/history.
- Analytics: GA4, PostHog, and Search Console own provider records; CardForge owns consent, event vocabulary, and owner report composition.
- Social publication: Meta owns external authorization/posts; CardForge owns approval, destination policy, scheduling, retries, and delivery history.

## Storage lanes

Library composes selected Pipeline governance through its existing action system and `EnvironmentToolLayer`; `OwnerContributorProgramPanel` / `OwnerAssetLibraryPanel` still own governance. Ephemeral selection pins include asset, lineage, submission, revision and publication state; a changed or missing exact submission blocks rather than substituting latest. Published selection uses the catalog's explicit submission link. Template/style revision entry verifies the selected current base through existing Owner endpoints, then uses the existing local Template draft or appearance editor; opening is read-only. Owner Library Pipeline discovery also offers a submission/revision-row mode, using the existing authorized `/api/pipeline` server query with independent type/status/search and 12-row pagination. Normal lineage view and Contributor visibility remain unchanged. Revision pages retain exact submission identity and current-publication pins; page results are not regrouped or filtered a second time in the browser. Global Pipeline operations retain program oversight, Studio map and Pipeline rules, and hand off revision discovery to the same Library queue. Per-artifact governance stays in the exact-target Desk/Library tool rather than a second global Asset library; unsaved or in-flight settings block queue navigation. Contributor editing stays on the selected owned editable revision.

Library Template previews resolve exact catalog IDs and use hydrated registry content only when the selected submission matches the explicit publication link and lineage. Historical/candidate revisions retain their own immutable source; names never substitute for Template identity, and missing sources are visibly unavailable. Personal copies keep their independent local preview. Displayed-revision contributor labels are separate from lineage participation; participation filters and exact eligible edit/retire targets retain their existing authority.

CardForge has four deliberate storage lanes.

### Browser workspace

`src/features/project` owns Zustand workspace state, IndexedDB persistence, account/guest scoping, first-account guest adoption before account hydration, revisioned compare-and-set writes, visible multi-tab conflict recovery, recovery snapshots, storage-health handling, local project assets, and portable project files. Sign-in always resumes an existing account workspace, including preserving unreadable account bytes for recovery; it never replaces that workspace with the guest lane. Autosave omits byte-identical persisted workspace updates; explicit saves still check the native expected revision. Keeping a conflicted tab open preserves its work without authorizing overwrite. Repeated identical conflict evidence stays available in the recovery banner instead of reopening a dismissed dialog; a newer revision can require a new decision. Only an account with no saved workspace automatically adopts guest work. Its first workspace, asset catalogs, and exact guest-source removal commit in one native transaction after required artwork is copied. Concurrent changes reject adoption without consuming guest work. When an existing account resumes, guest work remains separate for explicit backup/import. Persisted workspace and asset-catalog JSON retain account/project-scoped content-addressed references; mounted renderers and asset pickers acquire Blob object URLs on demand and release them after the last consumer. Browser package exports capture referenced artwork and frame bytes through bounded browser-native fetches into the existing package codec; inaccessible or unsupported linked artwork fails visibly without changing the workspace. Unresolved relative/CSS sources fail visibly; SVG bytes from remote, inline and local sources must pass the codec’s conservative self-containment check (UTF-8 geometry and local fragment references, no linked or encoded dependencies). Whole-workspace export scope remains unchanged. Browser package imports persist verified bytes directly as scoped Blobs and install references into runtime state instead of expanding package assets to Base64. Base64 data URLs remain accepted as legacy/input values and are externalized before persistence. When supported, CardForge reports the browser's current persistence state and offers a user-triggered `StorageManager.persist()` request with explicit “resilience, not backup” language. The browser workspace remains the normal working copy, local sets remain unlimited, and there is no parallel localStorage compatibility owner.

`src/features/editor-preferences` owns creator-local editor presentation preferences shared across authoring surfaces. `src/features/project` supplies the scoped browser persistence and one-way migration bridge for those preferences, but editor preference state is not Project document/package content.

### User-owned durable locations

Portable Set/Project files, browser-authorized local project folders, and connected providers own durable creator copies outside the browser workspace. `src/features/project` owns the shared v2 project package writer, v1/v2 compatibility reader, archive safety bounds, and revision contracts; each location adapter owns only its native permission, read, write, remove, and conflict lifecycle. Device File System Access saves stream the archive directly; download, Pipeline, MCP, and Google Drive boundaries that require a complete body use the same writer's bounded Blob form without redundant byte-array copies. New Desk/Library saves isolate one Set per package so a work container keeps one stable CardForge identity while gaining multiple location records. Each isolated Set package captures the exact revisions of every Template the Set intentionally references, including prepared Templates that have no generated Artifact yet; reopening the package loads those exact snapshots rather than silently substituting another local revision. The same validated `.cardforge` package owns import, export, provider transfer, Pipeline Set publication, and Published Set installation. Installing a published revision creates independently editable local identities; it does not introduce a starter schema, mutate Pipeline lineage, or create CardForge-owned durable creator storage. Google Drive stores work identity as `cardforgeWorkId` beside the exact provider and package revisions; updates preserve it even when an older Studio or MCP caller omits it. Local-folder writes are read back and decoded before CardForge reports success. Browser-only and local-folder work remain unavailable to remote agents unless the user explicitly hands it into the temporary Studio-document workspace or saves it to a server-reachable provider.

`src/features/project/model/workLocations.ts` owns destination capabilities for device, Google Drive, and local folders; Library composes that native contract. Copy and Move are separate commitments: Copy leaves the source unchanged, while Move may remove the source only after the destination package has been written and verified. Unsupported provider-to-provider paths require opening a device copy first rather than pretending CardForge operates a universal sync layer. The preferred save destination only orders new destination choices; existing attachments retain their destination. Older attachment metadata without proven package scope must be reopened before overwrite.

Ordinary Drive Open resumes the existing working Set by exact provider account and file identity. First Open maps portable entity identities into collision-safe local identities and retains the inverse map for subsequent saves; independent Copy creates detached identities. A writable linked Set coalesces ordinary browser edits into that same Drive document after a short idle period and reports its pending/saved/offline/conflict state in the Desk context. Project owns that working-session lifecycle; Desk orchestration composes it once for the focused Set, while the context rail receives only the resulting status and bounded repair/reconciliation actions. While that linked Set is open in a visible browser, CardForge probes only the exact Drive file metadata every 30 seconds and checks immediately again on focus or reconnect. If Drive has a newer saved revision and the browser copy is clean, CardForge downloads and refreshes that revision in place; if the browser also changed, CardForge preserves local work and stops automatic saving for explicit reconciliation. Read-only Drive collaborators may receive newer saved revisions but never gain write capability. This is shared-file freshness over one provider-backed document—not live co-editing, presence, CRDT state, or a CardForge universal sync protocol. Library never pools distinct Drive files solely because they share a portable work id. Historical multi-Set packages retain their package scope and cannot be overwritten by saving one Set or unrelated workspace content. Locations points to the canonical per-Set binding. Unreadable bindings remain unavailable instead of becoming a new save target. Folder detachment forgets matching CardForge handles without deleting files or claiming to revoke browser permission.

Package application uses the existing workspace slice policy in a detached draft, then commits workspace and asset/font catalogs in one IndexedDB transaction before installing the runtime state. Concurrent workspace/account changes and explicit installation cancellation abort application through the native transaction. Agent handoffs retain the workspace state from before download, so intervening edits reject the delayed install; cancellation propagates through document/artwork downloads and cannot apply an uncommitted draft. Merge preserves a different imported Template snapshot even when its historical runtime ID collides with another local design: exact matches remain shared, while conflicting snapshots are re-keyed locally with their lineage/provenance intact and every imported Set/Artifact reference remapped consistently. Recovery revisions always advance; failed hydration cannot authorize empty autosave, and original corrupt data remains recoverable. Current project open also awaits the completed-public-deletion evidence/repair transaction before exposing an editable workspace: confirmed deleted image/icon **content** becomes an explicitly blank but structurally retained layer, not a removed element; card-specific changes fork a personal Template and preserve shared history, bindings, children and live embedded copies. The blank state wins against canonical image-field materialization, rendered image fallback and legacy icon glyph defaults, and a deliberately refilled icon can render new art. Typed texture/background references clear only on exact completed proof. Portable saves ignore inactive blank-media references without dropping shared card text/data or live asset capture. The original browser workspace is preserved on failed evidence or CAS save; the scoped notice follows a committed repair. PR581 supplied the source correction and PR582's [recorded browser proof](https://github.com/pyralisxc/CardForge/pull/582#issuecomment-6488662226) executed the required recovery cases; neither proves a real hosted deletion. Recoverable catalog Trash/holds, physical deletion and immutable server history are separate: a 30-day deadline does **not** mean physical expiry is enabled. Emergency full editable backup and independent recovered-copy import are available without paid portable-project access. Artwork externalization deduplicates and batches native Blob writes; referenced recovery artwork is retained. Device Move also requires the original source state to remain unchanged before source removal. Drive-to-device transfer offers Copy while atomic external-source deletion remains unproven.

Library reports partial availability when a source fails but collection objects remain usable. It preserves the source's failure and recovery details alongside those objects; a search with no matches does not turn partial availability into an empty or wholly unavailable collection.

CardForge does not operate a durable first-party creator backup lane. Cloud Set Mirror APIs, agent workflows, tables, and lineage columns are retired. Portable files, authorized folders, and connected Drive own durable creator copies.

### Supabase platform state

Server-only CardForge code reaches Supabase through `src/infrastructure/database/supabaseServer.ts`, preferring `SUPABASE_SECRET_KEY` with a deploy-safe legacy service-role fallback. Browser-direct database writes are not a product path; direct browser object transfers occur only through server-issued signed URLs.

Supabase stores owner/public settings, legal/business identity, roadmap/votes, billing ledgers, contributor profiles/submissions/votes, asset registry state, campaign content/media/distribution history, contact history, temporary private Studio documents, and other shared control-plane records.

### Pipeline-owned Studio catalog

`cardforge_asset_registry` is the single runtime shared Studio catalog and discovery index. A published Template's linked immutable `cardforge_contributor_asset_submissions.source_payload` revision owns its structured document; the registry stores only the active pointer, routing, access, ordering, and discovery metadata. Embedded Template media is normalized once into content-addressed WebP objects recorded by `cardforge_pipeline_template_assets`, while revision JSON stores `cardforge-pipeline-asset://` references. Database constraints prohibit embedded Base64 in Template revisions and prohibit registry metadata from cloning Template documents. `data/pipeline-bootstrap` is importer input only and `public/site-fallbacks` is public-page fallback art only; neither competes with the registry.

Pipeline governance uses the registry's exact submission pointer as Live, not the newest row carrying a published status. `cardforge_pipeline_publication_events` records the exact revision and review snapshot whenever that pointer moves. Community review is unweighted, including self votes: one positive preference per Contributor per lineage, with revision-specific negative objections. Feedback on closed or historical revisions updates vote totals without rebalancing their lifecycle. Failed never-published revisions receive recoverable Trash metadata; previously published revisions remain History. Permanent cleanup is a two-phase service-role boundary: claim due rows, remove Storage bytes, then finalize only if the row is still non-live, never-published, unheld, and unreferenced.

Owner-authored corrections can prepare an exact published Template as a browser review draft, then submit an unpublished revision in the same Pipeline lineage. The persisted working Template owns the content lease and keyed-attempt receipt context; these are not authored content and do not enter portable packages or published payloads. The native transaction compares the current source, classification, registry pointer and routing, preserves creator/source attribution and owned artwork references, and allocates above the lineage high-water ordinal shared by all Template revision writers. Save remains local; review submission does not approve or publish. A separately approved promotion rechecks the same parent, and expiry uses the existing purge lifecycle without deleting parent-owned media. Reviewer source evidence is bounded, versioned metadata on that same submission, never a replacement for inherited creator notes. Evidence recording compares the exact candidate, live parent and prior evidence version; changed facts reset editorial review to pending, and approval compares the evidence version actually inspected. Technical hashes and paths do not establish publication rights or undisclosed AI history.

The Owner Content Health panel exposes every loaded finding and a downloadable read-only content review manifest, including coverage, identity, source, classifications, and proposed explicit physical formats. Set submissions do not require a Studio destination; health rules use native per-kind routing. The manifest proposes no invented classifications or revision identities. Authored-content updates use normal Pipeline revisions.

Classification validation, contribution forms, and Content Health share one policy: reusable textures, dividers, icons, images, styles, and fonts classified only as General may omit a specific use case. Templates and Sets still require a meaningful use case; unsupported labels never silently become an empty valid value.

Published discovery classification is an Owner operation in Content Health. The existing owner boundary reads the exact current registry/submission identity, then one service-role-only Postgres command compares lineage, revision, and previous taxonomy before changing tags. It follows native publication lock order and returns a retryable busy failure instead of waiting on a competing bootstrap publication. The existing taxonomy trigger updates discovery; authored payloads, votes, publication status, and lineage stay unchanged. `scripts/prepare-pipeline-catalog-modernization.mjs` produces read-only, source-backed proposals and native revision payloads; ambiguous or partially authored classifications require review. Its inventory must include the complete current submission taxonomy, semantic role, family, variant and compatibility snapshot before it emits a request. Tag-only proposals preserve those non-target values in both the expected baseline and proposed command; missing values are never inferred as empty or base.

`npm run pipeline:sync-defaults` imports missing stable IDs and referenced media without overwriting owner decisions or recreating tombstoned assets. Code owns finite Studio destinations/compatibility; Supabase owns live placement, ordering, featured state, and owner overrides.

Template Studio consumes that routing rather than inferring every placement from an asset's broad kind. Explicit `studioDestinations` win over the finite kind fallback. Template-derived card treatments stay on the current face and physical format, and front Templates expose published same-format backs as navigable counterparts. Foundation and border artwork may declare compatible portrait, landscape, or square orientations; Studio filters explicit mismatches while treating unclassified artwork as generally compatible. Published Library details explain the contextual Studio destinations for non-Template resources rather than presenting a disabled generic open action. These projections do not create a second catalog or duplicate the underlying revision.

## Core ownership

- `src/domain`: pure Artifact, Card, Template, Rendering, and Entitlements policy. In the shipped card specialization, one Artifact is one whole card identity; front/back are faces inside that Artifact, with a required front Template/data relationship and optional back Template/data relationship. Set exposes the generic Artifact identity/type seam while current creation and type-specific payload rules remain card-specialized.
- `src/features/app-shell`: creator interaction sessions, feature-owned action execution, shared Environment shell, contextual-tool boundaries, and compatibility Studio ingress.
- `src/features/creator-workbench`: focused Design/Generate/Output/Pipeline composition and workspace bootstrap over native feature owners.
- `src/features/desk`: user-facing Creator Spatial Environment composition, select-first Set objects, signed physical Desk and Set-local coordinates, transform-owned orthographic cameras, direct manipulation/edge-pan, marquee/touch/keyboard interaction, reflective organization, persistent Set/Artifact focus projection, context-rail actions, selection-scope action presentation, culling/LOD, ordered non-visual navigation, and return context over the native project and Library owners.
- `src/features/template-editor`: Template Studio session/draft lifecycle, canvas/layer/inspector commands, history, native Template-library commands, Save impact presentation, and personal/shared Template revision/fork decisions.
- `src/features/card-generator`: bulk card creation, direct single/compatible-multi Artifact content editing, generated-card editing, image controls, validation, derived Needs Work evaluation, and production exports. Desk remains the native presentation owner for Set/card organization.
- `src/features/card-rendering`: shared preview/rendering, rich text, vector shapes, thumbnails, appearance, watermarks, and transition presentation. Saved inline rich-text markers compose through the shared parser for editor reopening, canonical preview and export; combined marks do not introduce a second saved format. Renderer contract changes invalidate persisted pixel identities. `ArtifactScene` owns travelling pixels only while an Artifact moves between stack/board/focus/edit depths; once settled, the destination `ArtifactSlot` owns the visible card pixels and accessible interaction surface.

Desk and Set share canonical signed spatial primitives for world↔screen projection, Fit/Whole framing, zoom anchoring, edge-pan, and native Pointer Event gesture arbitration. Their cameras are explicit transform state rather than native-scroll projection; content bounds can change without relocating authored objects or Custom camera state. Focused Artifact inspection may still use its finite local viewport for deliberate magnified pan, but it is downstream of the same stable Artifact identity/physical geometry. Object owners retain selection and persisted movement; pinch and cancellation discard pending moves. Mouse dragging and keyboard nudging remain available. In focused-card mode, Desk derives a nearest cardinal neighbor from the current visible Set layout; fitted-card swipes, card arrow keys, and the compact Browse control change only transient focus/selection. A Set move records the displayed spread before switching an automatic arrangement to Freeform. Camera changes never alter layout geometry. The Environment shell owns the available viewport height; nested Studio uses that height, and optional Set organization controls disclose inline instead of permanently consuming the card field. Every lazy workspace tool shows a loading status before its implementation arrives.
- `src/features/project`: browser workspace/persistence/recovery/assets, Set → Template references, Template snapshot-safe package/import behavior, portable project/Set files, local-folder persistence, and connected-project adapters. Its client boundary is split by workspace, persistence, package, asset, provider, location, and UI responsibility.
- `src/features/account`: current Clerk-backed user projection, entitlement surfaces, ordinary signed-in account-tool capabilities, profile, and account administration.
- `src/features/billing`: Stripe checkout/portal/webhooks, product/support classification, durable billing event/subscription records, and reconciliation.
- `src/features/contributor-access`: Contributor identity/profile status/contribution-scope owner and the only runtime access owner for Contributor profiles. It does not gate ordinary signed-in Studio/agent work.
- `src/features/pipeline`: Forge Review submissions, voting, revisions, publication, attribution, Studio routing, archive/recovery, and registry operations.
- `src/features/studio-documents`: private account Studio documents and agent authoring tools. Agent card writes reuse the same Template authority and Artifact identity rules as browser Studio.
- `src/features/contributor-program`: public contributor recruitment/explanation.
- Historical site-proposal records and legacy database columns remain retained for audit, but they are non-authoritative: the runtime no longer reads or writes a proposal grant, no current Owner control can enable one, and the compatibility API always fails closed with `site_proposal_retired`.
- `src/features/marketing`: strategy, audiences, campaign containers, offer/claim policy.
- `src/features/marketing-content`: content packages, variants, canonical campaign media/derivatives/attachments, contributor workflow, review, and approval.
- `src/features/marketing-distribution`: destinations, encrypted provider connections, schedules, jobs, retries, manual-publication records, and provider-post mappings.
- `src/features/social-publishing`: stateless provider protocol adapters only.
- `src/features/public-site`: public copy, constrained navigation/home/SEO settings, public brand/marketing media, caches, public presentation, and server-gated contextual Owner editing on the native public surfaces. Anonymous RSC output never includes Owner controls or unpublished control payloads.
- `src/features/business-identity`: canonical operator identity.
- `src/features/legal`: immutable versioned legal publication.
- `src/features/contact`: contact/support routing and request history.
- `src/features/roadmap`: public roadmap, suggestions/voting, official status, settings, and owner roadmap operations.
- `src/features/analytics`: consent boundary, safe event contract, organic UTM policy, and owner provider reports.
- `src/features/experience-settings`: launch-time experience policy and sanitized public projection.
- `src/features/owner`: owner authorization, provider/database health, people/integration projections, append-only activity, and lazy composition of feature-owned controls.
- `src/infrastructure`: provider adapters and generic server infrastructure.
- `src/shared`: framework-independent utilities.
- `src/components/ui`: generic UI primitives.

Cross-feature consumers use declared public interfaces. `src/lib`, `src/store`, and `src/types` are retired root ownership lanes and must not return. The architecture report also prints feature fan-in/fan-out and public-interface export breadth as dependency-gravity review evidence; these are visibility signals, not arbitrary hard caps.

## Dependency rules

`npm run architecture:check` scans TypeScript imports and fails directly on ownership violations. There is no exception baseline.

- App Router composes features through declared interfaces.
- Features do not import App composition.
- Cross-feature imports use the target feature public interface.
- Client modules never import server interfaces.
- Domain/Shared/Infrastructure/generic UI retain one-way dependency direction.
- Feature dependency cycles are forbidden.
- Oversized files are review warnings, not automatic split requirements; split by responsibility when human traceability improves.

## Access model

- Free: local design/generation, portable Set packages, browser-authorized local folders, and one personally connected provider location such as Google Drive. A Free creator can keep and reopen their own work; provider permissions and storage limits remain provider-owned.
- Creator Pass: clean paid finished-output entitlement plus the longer private Studio work window and higher current beta capacity target. It does not gate portable-project or connected-provider access.
- Designer Pass: Creator Pass-grade Studio access plus the highest current beta Designer capacity target; it does not grant contributor access.
- Contributor: Creator Pass-grade output plus contribution/Pipeline capabilities according to the active contributor profile and granted scopes.
- Owner: protected Profile operations plus contributor-grade tooling.
- Public Clerk metadata is display-only; trusted access comes from Clerk private metadata and server-owned allowlists/policy.

`src/features/account/lib/accountExperience.ts` projects those independent axes into the shared product surfaces: plan (`free`, `creator`, or `designer`), active scoped contribution access, and explicit owner authority. Desk, Library, and Profile remain the same navigation environments for every account; catalog visibility, durable project/location capability, Pipeline scope/actions, focused Studio capabilities, and owner governance layer onto them. A `contributor` entitlement without an active Contributor profile grants no contribution surface, and every Forge Review HTTP mutation independently requires its exact contribution scope. In the Environment vocabulary, `member` means any signed-in account and never means Creator Pass.

Current account resolution uses Clerk's current-user identity directly; CardForge does not maintain a second session/profile fallback. Explicit user-id administration uses Clerk's Backend API.

Owner commercial grants are additive. The effective commercial plan is the stronger of an explicit `cardforgeOwnerCommercialPlan` and current valid Stripe access. Choosing Free removes only the owner grant. Ambiguous legacy paid metadata requires owner confirmation instead of timestamp inference or a silent downgrade. Contributor provider failures remain unavailable; they never become an empty roster or a signed-out/Free projection.

The scene uses one authored spatial hierarchy plus explicit camera projection and Motion only for interruptible depth travel. Wheel/drag motion remains direct, reduced motion skips nonessential travel, and the canonical card canvas/physical format determines Artifact dimensions. Front/back state follows Artifact identity through every depth. The transition overlay yields once travel settles; board/focus/edit destinations render inline and own their controls, avoiding permanent measured duplicates. Culling/LOD may reduce rendered detail but never changes scene membership or authored transforms. Geometry slots never own a second card renderer or persistence store.

## Card and Template model

Desk is the persistent creator environment. Set focus expands the selected Set object inside the same scene and exposes its saved Artifact organization; representative stack cards unfurl into the Set field instead of leaving a second miniature stack behind. Desk Set positions are signed personal workspace coordinates; Set Artifact positions are signed portable Set-local coordinates. Printable work uses canonical physical millimeters, with Template/CardFormat dimensions shared through Studio, Set layout, Desk presentation, snap, rulers, and output; unit display may be mm/cm/in or px only where a real pixel mapping exists. `feature:desk` owns the Desk/Set camera viewports, grid projection, direct manipulation, edge-pan, selection and focus composition; the shared shell allocates space but cannot reposition world layers. Ordinary entry uses Fit Work, Fit Selection/Whole are explicit camera commands, and direct manipulation enters Custom. Camera state is ephemeral and independent from content bounds, project/package/Drive/provider persistence, and authored coordinates. Grid/object/world overlays consume the same camera transform. Bounds and Set arrangement are content-derived rather than viewport-derived, so resizing the browser changes projection only. Choosing an Artifact keeps the Set mounted as continuity context while the same Artifact transitions into a focused destination; opening Design keeps that scene visible under the floating Studio tool layer. One context rail owns Desk → Set → Artifact → tool identity. Back/Escape unwinds depth while restoring the captured parent camera/selection, except when an open menu or selector consumes Escape first.

One card Artifact has stable identity, required front `templateId` + `data`, and optional `backingTemplateId` + `backingData`; front/back faces are not independent card Artifacts. A Set owns its Artifact membership/organization and an explicit list of reusable Template identities intentionally participating in that work. That Set reference may exist before generation and does not transfer Template ownership. Generating or moving an Artifact into a Set guarantees its front/back Templates are referenced there; removing the last dependent Artifact does not implicitly prune an intentionally referenced Template. Duplicating a Set creates a new Set plus new Artifact identities while preserving references to the same reusable Templates.

Templates have reusable lineage plus exact revision identity. A same-design Save advances the lineage; an intentional variant/fork creates a new lineage with provenance to its source. Runtime/local ID is not a substitute for lineage/revision semantics, and provenance does not transfer ownership. Saved Set packages capture the exact referenced Template snapshots. Loading an older snapshot never silently downgrades another Set's active Template, and a same-lineage newer revision is an explicit update choice rather than an automatic substitution.

Focused Artifact Edit stays inside the spatial Desk scene rather than opening CreatorWorkbench or a second card editor. Renderer-derived targets connect visible canvas elements to the existing field grammar: selecting a variable region opens its Artifact data in the persistent inspector, while Template-owned regions explain their shared ownership and offer Design Template. Draft pixels update on the same scene Artifact; Save & Done updates the native project store, Cancel retains the persisted card, and explicit Edit mode prevents field taps from competing with swipe/pan navigation. Compatible multi-Artifact Edit reuses the same field grammar with mixed-value presentation and sparse patches; only explicitly touched fields are changed. Different front Templates are not treated as compatible merely because they share field-key strings, and same-front/different-back selections may edit only the safe common front scope.

Design from Artifact focus or the card editor opens the current face's Template in the existing Studio designer without cloning or rebinding on entry. Template Save is the consequence boundary: shared changes remain on the reusable lineage; Artifact-scoped divergence creates a personal Template variant only when the creator commits it and atomically rebinds the captured Artifact scope. Cancel/no saved divergence persists no variant. Intentional Template field removal clears that field's stored Artifact data for the adopting scope. Adding a required field without a usable value may intentionally leave linked Artifacts in derived **Needs Work** state; Needs Work is computed from current Artifact data against the current Template contract and is not another persisted workflow status.

Design uses the existing Template snapshot history for text and field contracts as coherent edits; rich-text controls use that same history inside Design. A successful same-document Save returns the canonical record captured by the local persistence owner, advances that saved baseline, and reconciles its source/revision metadata into the working copy and existing history without clearing valid selection or replacing newer authored edits made during persistence. A genuine document or fork identity change resets editing history; independent rich-text editors retain their own native history.

Deleting a front Template removes its front-dependent card Artifacts after explicit impact confirmation. Deleting a Template used only as a card back preserves those Artifacts as front-only and clears the back reference/data. Pipeline retirement/publication remains distinct from personal browser deletion.

Generate, Output, and Pipeline use non-modal desktop docks or compact mobile sheets while keeping the creative scene mounted and continuous; on compact screens a sheet Task owns the work viewport instead of asking the scene and long-form controls to compete for space. Provider handoffs and consequential confirmations remain genuinely modal. The interaction session's `CreatorToolPresentation` is the only tool-presentation contract. The shared host restores focus, unwinds history, isolates tool crashes, protects outgoing navigation/reload, and can reject a dirty close without imposing a modal focus trap on routine creative tools. Template Editor owns reusable front Templates and separate card-back Templates; Card Generator owns one bulk generation runtime, rendered-card editing, validation, and output. The dedicated single-card form is intentionally retired; individual changes use direct Template/card editing. Focused card actions reuse native image export, sharing, and portable single-card package output. Design receives typed matching-back/edit-back/manage-back intents from entry surfaces and executes the existing authoring workflow. Library Templates can be edited without creating a Set. Pipeline testing creates an independent local identity. ## Canonical rendering doctrine

CardForge has one canonical visual rendering implementation. Templates and structured card data are interpreted only by the browser CardPreview/export pipeline. Studio exports, assistant previews, and future downstream output systems must reuse render artifacts produced by that renderer or invoke that exact renderer with an explicit profile; integrations must not independently reinterpret Templates for convenience.

Authored text-element fonts resolve through the domain font-to-CSS mapping in the shared text renderer, just like field-contract fonts. Rendering a data-selected font must not depend on a build scanner having encountered its utility class; explicit field formatting retains precedence over the element default.

Card foundations may explicitly choose Cover, Contain or Fill on the existing Template. That authored fit survives portable and agent document round trips and is shared by Design, previews, thumbnails and production rendering; unspecified legacy designs retain their existing placement. A foundation synthesized into appearance normalization is not painted a second time when an explicit fit is selected. Independent material layers keep their own sizing. Fit changes neither source artwork nor physical trim/bleed geometry, and cannot manufacture safe background content.

Studio's empty default Divider adopts a selected catalog item's recommended dimensions once; customized or already asset-backed geometry stays authored. Uploaded material texture strength is rendered as an independent layer by the shared appearance surface, preserving the fill stack, border, text and source identity. The same painter serves Design, Library previews and exported cards. Vector rectangle corner radius uses authored element units for both geometry and fill clipping; Solid, Double and None are native vector stroke treatments, without inventing rounding for path primitives.


Canonical render artifacts are immutable derivatives bound to source identity, source revision, render subject, face, output profile, and a renderer contract version. A source revision can therefore remain unchanged while a renderer fix produces a new derivative contract, preventing stale pixels from surviving a rendering bug fix. Private render artifacts are cache/output data, not a second source of truth.

MCP static creative review returns native PNG display images derived only from these canonical CardForge-rendered artifacts.
