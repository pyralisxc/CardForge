# CardForge Risk Register

Last updated: September 19, 2026

Only unresolved or explicitly accepted risks belong here. Closed work belongs in Git/provider history and current operating instructions belong in `docs/operations.md`.

| Area | Risk | Priority | Status / next proof |
| --- | --- | --- | --- |
| Migration provenance | Older provider migration timestamps do not consistently match repository filenames, so an edited or removed historical migration can leave Git and a provider ledger out of sync. | P1 | Controlled. On September 16, authenticated Supabase history and the live schema confirmed that the staging-only `20260912033706` entry was the already-applied Drive resource-key migration tracked in Git as `20260911213000`; the provider ledger was reconciled without changing schema or data. Keep future migrations additive and immutable, compare the production tail before rollout, and never guess from filenames alone. |
| Drive concurrent external edits | Native resumable update and explicit deletion use revision preflight; an external change between preflight and final write is not proven protected atomically. | P1 | Open. On September 16, independent browser sessions opened one disposable Drive Set, one saved a newer revision, and the stale session's update was refused with an explicit recovery path; the newer Drive revision was preserved. Drive-to-device Move is disabled; Copy preserves the source. Lost commit receipts forbid automatic replay. Known missing, dirty-remote, access, authentication, not-found, and confirmed-receipt states now pause client autosave until an explicit recovery action. This does not prove a change that lands between another writer's preflight and final upload, so retain the atomic-race risk until a controlled final-upload overlap succeeds safely. |
| Drive collaborator and invalidation acceptance | Shared-folder, shared-drive, resource-key, reconnect, and capability projection are implemented, but collaborator-created/read-only file authorization and missed external move/delete/revocation handling have not been accepted end to end. | P1 | Open provider acceptance. On September 16, the secondary signed-in Drive account could see the shared QA folder and its fixture files, while CardForge correctly kept them out of that account’s Library until an explicit Picker authorization. Test a collaborator-created file through explicit `drive.file` authorization, verify read-only/editor behavior, then exercise external move, delete, revoked access, reconnect, and missed/expired notification recovery. Current provider content and capabilities must win; shared listing is not realtime collaboration. |
| Google OAuth publishing | Production Google authorization remains External/Testing, so broader users cannot authorize and Testing refresh grants remain short-lived. Production and Preview/testing are isolated in separate Google Cloud projects; the live production Privacy Policy contains the Drive access/storage/disconnect and Google Limited Use disclosure, and CardForge now fails closed if Google returns or a saved connection contains a broader Drive scope than `drive.file`. | P1 | Open provider decision. Complete production Branding/domain verification and Data Access verification in Google Auth Platform, publish the production audience when Google permits it, confirm the production Picker restrictions, then verify authorization and open/save/disconnect with a Google account that is not a Preview test user. Keep Preview/testing isolated and in Testing. |
| Legacy commercial grants | Older private paid metadata does not always distinguish an owner grant from Stripe projection. | P1 | Controlled. Preserve access and require explicit owner grant confirmation; no timestamp inference or automatic destructive migration. |
| Billing provider acceptance | Current Stripe projection and additive grants pass focused tests and independent review; the disposable native multi-subscription checkout/reconcile experiment is unfinished. | P2 | Deferred acceptance follow-up. No paid fixture was activated. Preserve current-provider reconciliation and service-owned locking; complete the sandbox journey before a broader billing rollout. |
| Social publishing | A credential, wrong destination, scheduler retry, or partial approval could expose media or publish an unapproved post. | P1 | Open; hard-disabled. Keep extended-contribution/native Meta gates off until protected media, scoped contributors, encrypted tokens, exact destinations, idempotent claim/retry, harmless publication, and durable delivery postflight in `docs/operations.md` pass. Communities remain manual-only. |
| Large local projects | Long artwork sessions can exceed browser quota or degrade recovery despite IndexedDB, persistence requests, actual-write failure reporting, snapshots, and project export/import. Complete-body download/provider boundaries also materialize one size-bounded package Blob, while authorized device-file saves stream. | P1 | Accepted. Browser capacity is not a CardForge allowance and persistence is not a backup. Revisit after a real quota/recovery report or when a provider supports a practical streaming upload contract. |
| Print prepress | Browser export does not provide CMYK, PDF/X, or printer-specific duplex certification. | P1 | Accepted. CardForge does not claim those capabilities; revisit with a dedicated print-production release. |
| Export acceptance | Browser success does not prove every downloaded PDF/TTS artifact or simulator import at large-set limits. | P2 | Accepted with manual checks. Inspect affected artifacts and perform a real TTS import after renderer/export changes. |
| Solo maintainer | A PR author cannot independently approve their own change, so one required approval would deadlock releases. | P2 | Accepted while `@pyralisxc` is the only trusted code owner. Keep resolved threads plus CI, Vercel preview, and live workflow checks; require one approval when a second trusted reviewer joins. |
| Provider presentation | A configured Stripe receipt path and Resend reply-to header do not prove one customer receipt email or an inbound reply round trip. | P2 | Manual proof remains. Complete these naturally or with an explicitly approved test; do not mutate a real customer merely to manufacture evidence. |
| Repository security monitoring | GitHub Dependabot security alerts and secret scanning are disabled, and no code-scanning analysis is configured, so the repository has no hosted alerting backstop for newly disclosed dependency or code issues. | P2 | Open founder/provider configuration decision. On September 16, the checked-in production lockfile was independently audited and is clean after the Hono 4.13.8 and current dependency-maintenance updates. Before enabling hosted scanning, confirm the GitHub plan/cost and desired maintainer notification policy; do not represent unavailable scanners as a clean result. |
