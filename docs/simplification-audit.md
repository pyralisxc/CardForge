## Judgment and evidence boundary

### Product outcome and executor mandate

Cameron's endorsed goal is to help creators turn structured information into coordinated designed Sets, keeping them easy to revise, organize, save and produce. The central promise is **design once → add information → generate a consistent Set → revise without starting over**. The spatial Desk serves recognition, comparison and organization; controls and animation earn their place by supporting that outcome. Preserve the broader sequence in `product-direction.md`; do not narrow the engine to MTG or introduce separate editors for each market.

Near-term acceptance is an unfamiliar creator completing this journey with a representative sanitized fixture:

| Creator outcome | Evidence required |
| --- | --- |
| Start from a sample or layout, bring structured data, generate a Set | The creator understands field mapping and validation, sees consistent results, and can recover an invalid row without restarting. |
| Compare, sort and revise individual cards | Finding and selecting work is predictable; changing a browse view does not silently overwrite authored placement or order. |
| Change the shared design | Linked cards update predictably; the scope of a template change is clear; card-specific information and intentional overrides survive. |
| Save editable work to a clear destination | The creator can name the destination, recognize unsaved local changes, distinguish Open from Make a copy, and tell whether Drive actually accepted the save. |
| Produce useful output and reopen later | Output is visually usable; reopened work retains data, design, assets and organization, and the next edit continues the intended document. |

**Mandate for the future executor:** perform an independent audit before implementation. ## Findings and concrete cuts

### F1. Visible-work correctness crosses too many geometry boundaries

**Observed failure; source-proven complexity; causal diagnosis still open. Priority P1.**

[`ArtifactScene`](../src/features/card-rendering/components/ArtifactScene.tsx) separates accessible layout slots from a fixed full-window layer that paints cards. It measures slots, picks the highest-depth slot per card, computes intersections from ancestor `data-scene-viewport` rectangles, and projects Motion transforms/clips. Therefore an accessible card can exist while its visual projection is clipped, outside the visible region, or absent. That explains why the earlier accessibility result cannot clear the incident; it does not identify which condition occurred.

The geometry path spans [`DeskOverviewSurface`](../src/features/desk/components/DeskOverviewSurface.tsx), [`Desk CSS`](../src/features/desk/components/Desk.module.css), [`FocusedWorkSurface`](../src/features/desk/components/FocusedWorkSurface.tsx), and [`FocusedSetArtifactSurface`](../src/features/desk/components/FocusedSetArtifactSurface.tsx). Focus changes an absolute 1200 × 720 Desk world into percentage-sized geometry using `!important`; several nested wrappers then rely on `height: 100%`, `min-height: 0`, and hidden overflow. Inside that chain, controls consume space and the card stage flexes into the remainder. Mobile adds a Desk sizer margin and further focus overrides. These are real coordination costs, not proof that any individual rule is wrong.

Desk camera uses local zoom/scroll refs; Set camera uses interaction-session coordinates synchronized with native scrolling; focused-card camera uses [`useArtifactViewport`](../src/features/card-rendering/hooks/useArtifactViewport.ts). Distinct coordinate spaces are legitimate. The unnecessary cost to remove is multiple owners deciding available height and restoration timing for the same space.

**Cut:** give the Environment surface one explicit viewport contract and one owner per scroll region. Derive focused layout directly from that contract; remove superseded focus-size overrides only after equivalent geometry is demonstrated. Retain the canonical renderer and existing shared gesture owner. Before retaining exact same-DOM-node animation as an absolute requirement, weigh its user benefit against maintaining the projection/clip layer. A simpler render composition is an alternative to evaluate, not an authorized rewrite.

**Proof:** capture deployed SHA, slot/stage/ancestor rectangles, computed clipping, camera and scroll values on the failing saved Set before touching it. Reproduce reload and Back at 1279 × 585, shorter desktop windows, 125–200% browser zoom, portrait and landscape mobile, expanded controls, browser toolbar changes, and keyboard-open editing. Require a nonzero unobscured card area and operable controls, not only card counts or `toBeVisible()`.

### F2. Recovery bypasses the normal revision-safe write owner

**Source-proven divergent path; revision-reuse consequence reproduced with actual source and fake IndexedDB. Priority P1, high-risk implementation.**

Normal [`createScopedProjectStorage.setItem`](../src/features/project/persistence/projectPersistenceScope.ts) serializes writes per workspace, uses [`compareAndSetBrowserWorkspaceValue`](../src/features/project/persistence/indexedDbStorage.ts), advances revision, and broadcasts the change. `restoreBrowserWorkspaceRecovery` reads the recovery value separately and writes it through `createBrowserKeyValueStorage(...keepRecoverySnapshot)`. It does not use that queue, expected-revision check, or broadcast; restoring the raw prior envelope can move the current revision backwards.

The low-level restore transaction does preserve the then-current value as the next recovery copy. Preserve that useful reversibility. It does not make restore participate in the normal concurrency protocol. A concrete risk is revision reuse: if a stale tab expects revision N and recovery replaces revision N+1 with the old N envelope, that stale writer may again satisfy the numeric compare-and-set. An in-flight autosave can also race the restore path. No actual overwritten user work was observed. An isolated probe confirmed revision 2 → restore old revision 1 → stale tab expecting 1 successfully writes. See the reproduction appendix.

Related read-path issue: the workspace `getItem` catches failures while externalizing legacy Base64 artwork and then quarantines/removes the current key. An asset-write failure or revision conflict in this path can take the same fallback as corrupt JSON. The initial IndexedDB read itself is outside this catch, so this is not a claim that every read timeout becomes empty state.

**Cut:** one project-owned commit path for ordinary save, recovery, and persisted-format conversion, built on IndexedDB transactions. Restore the selected payload as a fresh monotonically increasing revision, retaining the displaced current payload. Preserve unavailable/conflict versus corrupt meaning; migration I/O failure should leave the current workspace recoverable and retryable. Do not add a second recovery ledger or sync service.

**Proof:** two-tab stale writer after restore, queued save during restore, missing recovery, quota failure during legacy asset externalization, and a concurrent migration/write. Assert durable bytes, new revision, displaced recovery, and boundary result—not just a successful reload.

### F3. Drive Open forks identity; Library then collapses distinct copy identities

**Source-proven representation loss and misleading detail. Priority P1.**

[`buildAccountLibraryItems`](../src/features/storage-management/model/accountLibrary.ts) groups by `workId`. Each `AccountLibraryLocation` has source/status/label but no provider file identity or revision. Every matching Drive record appends a location and overwrites the aggregate `driveFileId`, provider revision, timestamp, and link. With multiple Drive files for one work ID, the last encountered record wins those references. The data model accepts this input; occurrence in Cameron's live Drive was not verified.

There is an additional exact mismatch: `driveProjectRevision` is overwritten only if the incoming project revision is truthy, while `driveFileId` is always overwritten. A later copy without a project revision can leave an earlier copy's project revision beside the later file ID. That is a provenance defect even before assessing a downstream action.

Local Sets start with `Device only` and `updatedAt: null`; the merge never revises the detail text. Provider time replaces aggregate time, obscuring the distinction between local edits and provider freshness. [`useAccountLibraryProjection`](../src/features/storage-management/hooks/useAccountLibraryProjection.ts) does not supply a local edit timestamp. Local-only Recent cannot order by actual edits from this projection. Names are deliberately not the merge key.

**Cut:** preserve explicit document/copy records carrying provider identity, revision, permission, and observed timestamp. A shared portable work ID can describe a relationship; it must not flatten distinct remote documents into one implicit save target. Derive details and source counts from those records. Require the exact copy at the action boundary. Retain existing provider revision enforcement; do not invent automatic reconciliation or infer equivalence from names. A local-only timestamp should be honestly unknown until its owner provides it.

**Proof:** same name/different IDs, same work ID/two Drive files in reversed order, missing revision on the second file, browser changes after a Drive save, and a permission-lost folder. Verify what opens/deletes/saves, not only row text. Current Delete device copy labeling distinguishes local deletion; this finding does not claim all deletes target the wrong copy.

#### Drive lifecycle: confirmed implementation facts

The concern about having to “load a Drive file into the browser” contains three different issues: fetching bytes to edit, persisting a recoverable working representation, and creating another document identity/tile. The first is necessary for the current browser editor; the second is reasonable for recovery/offline continuation. The third is a product choice, and ordinary Open currently does create new identities.

| Boundary and owner | Current behavior at the audited SHA |
| --- | --- |
| Discovery — [`googleDriveProjectStore`](../src/features/project/server/googleDriveProjectStore.ts), [`accountLibrary`](../src/features/storage-management/model/accountLibrary.ts) | Lists authorized custom `.cardforge` ZIP files in the configured folder, with private app properties, revisions and optional thumbnail. This is not a generic Google Docs editor or a view of every file in My Drive. Tiles pool by `cardforgeWorkId`, not by name or the local binding's file ID. |
| Ordinary remote Open — [`googleDriveProjectTransfer`](../src/features/project/client/googleDriveProjectTransfer.ts), `openGoogleDriveProject` | Downloads the package, validates source revision, then invokes `applyProjectDocumentToWorkspace(document, 'copy')`. There is no reuse lookup for an already-open `fileId` in this function. |
| Materialization — [`projectWorkspaceDocument`](../src/features/project/client/projectWorkspaceDocument.ts), [`instantiateProjectDocumentCopy`](../src/features/project/model/projectDocument.ts) | Copy mode assigns fresh Set/card/template/style/tag/asset-catalog IDs, remaps relationships, merges into the current workspace and persists it. It also applies imported output preferences. Binary content-addressing can deduplicate bytes; it does not prevent these new logical identities. |
| Attachment — `googleDriveProjectTransfer` | For a one-Set package, the new local Set receives a binding to the original Drive `fileId` and observed provider/package revisions. It is a new local instance that can write back to the original file, not a fully independent detached copy. Bindings are keyed by local work ID plus an attached-work pointer. |

| Save — `saveCardSetToGoogleDrive`, [`ProjectWorkLocationDialog`](../src/features/project/components/ProjectWorkLocationDialog.tsx), [`GoogleDriveProjectStoragePanel`](../src/features/storage-management/components/GoogleDriveProjectStoragePanel.tsx) | Browser persistence is local. | Multiple files / historical workspace packages | Multiple files with one work ID lose individual target identity in projection, as described above. Never deduplicate those Sets by title.

One predictable identity sequence needs a regression fixture: file F contains work A → Open creates local B bound to F → discovery still advertises F as A, so B cannot pool with F by work ID → saving B to F advertises B → any remaining local A is now separate. A second remote Open before saving creates C, also bound to F. Revisions constrain later saves but do not make B/C the same editable document. This is why a label-only fix is insufficient.

#### Drive previews: native path exists, delivery is incomplete

Discovery already requests `thumbnailLink`; the model carries it into `workPreview`, and [`DeskWorkPreview` in Desk.tsx](../src/features/desk/components/Desk.tsx) renders it directly with an `<img>`, falling back on image error. No full editor import is required by that path. However, current upload metadata contains no `contentHints.thumbnail`, and the inspected package model/codec/browser assembly has no dedicated preview derivative contract. An arbitrary custom ZIP should not be assumed to receive a useful automatic card thumbnail.

Google's [metadata/thumbnail guidance](https://developers.google.com/workspace/drive/api/guides/file-metadata) supports app-supplied PNG/GIF/JPG thumbnails for file types it cannot preview. Supply them on create/update; content changes invalidate old thumbnails. Native thumbnail links are short-lived and private-file retrieval requires credentials. The [Files resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files) also cautions against direct web-app use of these links because of CORS. The current raw image element supplies no CardForge-managed provider authorization or refresh path. This is a delivery risk requiring private-file/expiry proof, not proof that every returned URL fails.

**Minimum candidate:** generate a representative derivative through the existing canonical rendering owner when explicitly saving a Set, attach it through Drive's native thumbnail metadata, and display authorized native thumbnails before opening. Reuse existing card rendering / [`render-artifacts`](../src/features/render-artifacts/model.ts) capabilities after checking their input/lifetime fit; do not create another renderer or assume transient render links are durable previews. If a same-origin authenticated fetch is necessary, constrain it to the user's authorized file ID and provider URL obtained server-side, with private caching and bounded bytes. Do not make thumbnails public, persist expiring URLs as identity, add a CDN, or accept arbitrary proxy URLs. Keep a clear absent/expired/unavailable/permission-required fallback. A preview failure must not force import or prevent opening an otherwise readable file.

Existing files without thumbnails remain usable. Do not backfill them by silently downloading all packages or modifying their metadata. Consider an explicitly requested preview/backfill action only after the native save path is proven. Thumbnail generation failure must have defined behavior independent of whether document saving succeeded; the UI cannot claim the document was unsaved when Drive committed it. Original artwork, editable package data and export-quality rendering remain authoritative; thumbnails are disposable derivatives.

#### Cleaner document UX and alternatives

**Recommended direction:** one visible object for an intentionally opened remote document, showing “Google Drive” as its destination and an honest local working state. Opening fetches/decodes into the existing persistence owner, retains or deliberately maps its document identity, and reuses the working session for that exact provider/account/file. Resume local edits when present; offer an explicit refresh/compare decision if the remote revision changed. Do not overwrite uncommitted local work to make Open appear idempotent. Two independent Drive files remain distinct save targets even if package work IDs match; expose their relationship/copies in details instead of choosing whichever discovery row ran last. Reserve new identity for **Make a copy**, with a clear destination and attachment policy.

Keep three identities explicit: **remote document identity** is the authorized provider/account/file tuple; **portable work identity** is the Set identity carried by the package and can be shared by copied files; **browser runtime entity IDs** identify entities inside the editor's current namespace. Ordinary Open should be idempotent for the same exact remote source, not for every file with the same portable work ID. A provider-file-keyed working session with a stable collision-safe mapping is one possible minimal solution within existing persistence; the executor may propose a simpler coherent design after inspection. Do not blindly delete rekeying or merge by portable IDs: two distinct files copied from the same package must remain independently editable without their cards/templates overwriting or cross-linking each other. Preserve collision-safe instantiation for intentional import/copy. Make a copy should establish an independent target and explicit lineage, not silently keep writing its source. Refresh must distinguish a clean working state from unsaved edits and resolve remote change without overwriting either side. This is a behavior contract and a candidate design, not a prescribed new session-store architecture.

| Same-document working state + automatic Drive saves | Could reduce user effort, but adds real requirements for upload coalescing, in-flight edits, exact revision conflicts, uncertain completion and offline recovery. Not requested or implied by Open. Evaluate only after identity and explicit save acceptance are reliable; no universal sync engine. |
| Current import-copy workflow with better labels | Lowest implementation cost, but does not fulfill the expected “open my Drive document” interaction. It is appropriate for an intentional import/Make a copy action, not the recommended ordinary Open. |

Google's [download guidance](https://developers.google.com/workspace/drive/api/guides/manage-downloads) provides file-content retrieval for blob files; it does not give this custom ZIP Google Docs-style live collaborative editing. CardForge still needs decoded data and assets locally to render/edit, plus durable recovery where appropriate. Avoid promising zero local data or live sync. The native provider owns authorization, file identity, revisions and transfers; CardForge owns how its authored document maps to an open working session and how that state is explained.

Failure handling must preserve the existing [`googleDriveBoundary`](../src/features/project/server/googleDriveBoundary.ts) distinctions for reconnect, permission, limit and transient unavailability. The prepare path checks expected provider/package revisions before upload; F12's race remains unproven against real Drive. Browser upload errors are more coarsely wrapped than API failures, and a binding write can fail after the provider committed: retain the successful file/revision and make recovery actionable. A source descriptor's `serverReachable: Boolean(binding)` is attachment presence, not a live reachability check. Offline local work may continue if already materialized; reconnect/unavailability must not become “Device only,” blank work or a successful remote save. Any recovery copy stays intact until the authoritative writer confirms durable replacement.

#### Decisions and proof before implementation

Resolve three product questions in the executor's revised recommendation: (1) explicit Save to Drive as the initial model or a separately scoped autosave requirement; (2) intentional independent-copy versus linked-copy meaning, including shared template identities; (3) historical multi-Set package behavior and whether ordinary save may ever include unrelated open work. The recommendation above favors explicit saves, exact remote document targets and one-Set save scope. Those recommendations do not authorize converting existing files or collapsing authored copies.

Use sanitized fixtures for: open F twice; reload browser and resume; local dirty B plus externally changed F; A/B files with equal work ID in either list order; identical titles/different IDs; existing shared template IDs; workspace package alongside unrelated local work; failed materialization/binding write; upload committed but response/binding unavailable; read-only file, revoked authorization, offline state and limits. Assert stable intended identities, exact target, untouched unrelated work, recovered edits, unchanged authored content on failed open, and accurate status. Existing incremental workspace application writes assets/settings before the final persistence call, so failure atomicity must be demonstrated rather than inferred from a rejected Promise.

Preview proof requires a controlled private custom package with/without a supplied thumbnail, expiry/refresh, revoked permission, stale thumbnail after save and derivative failure after successful document commit. Verify before-open recognition without editor import and without public exposure. No such user-file mutation was performed here. Sequence this work with F1/F2/F3/F12: first agree identity/save semantics and reproduce the failure safely; fix ordinary Open and exact copy targeting in the existing owners; add trustworthy working/save state and native previews; then prove the full unfamiliar-creator journey. Toolbar consolidation can support that journey but cannot substitute for correct document ownership.
